# Structured Reference Catalog: Exploitation-Context Classification Sources\n\n## Source 1: MITRE ATT&CK STIX (`x_mitre_platforms` / `x_mitre_domain`)\n\n**Authoritative maintainer:** MITRE Corporation  \n**Schema:** STIX 2.1 (STIX Bundles at https://github.com/mitre/cti)  \n**Object types:** `attack-pattern` (techniques), `relationship` (technique-subtechnique, technique-tactic)\n\n### Execution-context dimensions captured\n\n| Dimension | ATT&CK Field | Values |\n|---|---|---|\n| Execution domain | `x_mitre_domain` | `\"enterprise-attack\"`, `\"mobile-attack\"`, `\"ics-attack\"` |\n| Execution platform | `x_mitre_platforms` (list) | **Enterprise:** `Windows`, `Linux`, `macOS`, `Network`, `SaaS`, `AWS`, `Azure`, `GCP`, `Azure AD`, `Office 365`, `Google Workspace`, `Containers`, `Kubernetes`, `Identity Provider`, `PRE`; **Mobile:** `Android`, `iOS`; **ICS:** `Windows`, `Linux`, `Network`, `Control Server`, `Data Historian`, `Engineering Workstation`, `Field Controller/RTU/PLC/IED`, `Human-Machine Interface`, `HMI`, `Input/Output Server`, `Operator Workstation`, `Protection`, `SIPS/PR`, `None` |\n| Delivery context | None | Not captured |\n| Exploit complexity | None | Not captured |\n\n### How Phase 1 LLM could query it\n\nDownload the STIX bundle (`https://github.com/mitre/cti/raw/master/enterprise-attack/enterprise-attack.json`) and index by technique ID. A CVE's ATT&CK techniques map directly to `x_mitre_platforms`. E.g., `T1611` → `[\"Containers\"]`; `T1078.004` → `[\"AWS\",\"Azure\",\"GCP\"]`; `T1613` → `[\"Containers\"]`. For domain: if technique appears only in `ics-attack` bundle, it is ICS-exclusive (no other matrix carries it).\n\n### Pros\n- Authoritative, maintained quarterly, ~95%+ coverage of real-world techniques\n- Cloud merged into Enterprise in ATT&CK v18 (Oct 2025): `AWS`, `Azure`, `GCP`, `SaaS`, `Office 365` all present as first-class platforms\n- `Containers` platform (added v12) + `Kubernetes` (added v13) explicitly tag container-native techniques\n- Technique-level resolution — not CVE-level, but technique→platform is stable\n\n### Cons\n- No delivery_vector at all\n- No exploit_complexity dimension\n- Domain (`enterprise`/`mobile`/`ics`) is matrix-level, not technique-specific — the technique is the right granularity\n- STIX bundle is 3-5 MB; requires local caching and refresh cycle\n- No direct \"execution_surface\" concept — must be *inferred* from platform membership\n- `unknown` cases require keyword fallback\n\n**Recommendation for Phase 1:** Use `x_mitre_platforms` as primary execution surface signal. Map platform → your enum: `Containers`/`Kubernetes` → `multi_hop`; `AWS`/`Azure`/`GCP`/`SaaS` → add `cloud` to enum; `Android`/`iOS` → add `mobile` to enum; `Windows`/`Linux`/`macOS` + `client` keywords → `client_side`; else `server_side`.\n\n---\n\n## Source 2: CVSS 4.0 Specification\n\n**Authoritative maintainer:** FIRST (Forum of Incident Response and Security Teams)  \n**Spec version:** 4.0 (https://www.first.org/cvss/v4.0/specification-document)  \n**Format:** Vector string (e.g., `CVSS:4.0/AV:N/AC:H/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H`)\n\n### Dimensions captured (vs. your 4 enums)\n\n| Your Enum | CVSS 4.0 Equivalent | Values Available |\n|---|---|---|\n| `exploit_vector` | Attack Vector (AV) | `N` (Network), `A` (Adjacent), `L` (Local), `P` (Physical) — **no cloud/container/api/IoT/OT** |\n| `exploit_complexity` | Attack Complexity (AC) | `L` (Low), `H` (High) — **\"medium\" is absent; `AC:M` does not exist in 4.0** |\n| *(missing in your schema)* | Attack Requirements (AT) | `N` (None), `P` (Present) — new in 4.0; captures prerequisite deployment/condition |\n| *(missing in your schema)* | Exploit Maturity (E) | `X` (Not Defined), `A` (Attacked), `P` (Proof-of-Concept), `U` (Unproven) — Threat metric |\n\n### What CVSS 4.0 does NOT add\n- No Attack Surface (AS) metric\n- No new AV values beyond N/A/L/P\n- No delivery vector field\n- No execution context field\n\n### How Phase 1 LLM could query it\n\nParse the CVSS vector string. Your `exploit_classifier.py` already does this via `parse_cvss_vector`. Map: `AV:N` → `remote_network`; `AV:A` → `adjacent_network`; `AV:L` → `local`; `AV:P` → `physical`. For `exploit_complexity`: `AC:L` → `low`; `AC:H` → `high`; **drop `medium` entirely** (CVSS 4.0 confirmed no medium).\n\n### Pros\n- Available for every CVE with a CVSS score (majority of NVD)\n- Machine-parseable vector string — no NLP required\n- AT (Attack Requirements) is a new qualitative signal for prerequisite conditions\n- E (Exploit Maturity) supplements confidence scoring\n\n### Cons\n- `exploit_vector` is too narrow: `AV:N` collapses client-side email exploits with server-side HTTP exploits\n- No delivery_vector at all\n- `medium` complexity gap — must decide how to handle CVSS 3.x `AC:H` maps to `high` and there's no `medium` in 4.0, but old CVEs may have `medium` in 3.x vectors (map to `medium` as-is, do not coerce to `high`)\n\n**Recommendation for Phase 1:** Keep CVSS 4.0 AV as the authoritative `exploit_vector` anchor. Use AT (Attack Requirements) to refine confidence — `AT:P` means the exploit is conditional, which correlates with `exploit_complexity:medium` or `high`.\n\n---\n\n## Source 3: CPE 2.3 Dictionary / NVD CPE API\n\n**Authoritative maintainer:** NIST / NVD  \n**Spec:** CPE 2.3 (NIST SP 800-126 rev 3)  \n**API:** `https://services.nvd.nist.gov/rest/json/cpes/2.0`  \n**Format:** CPE Name URI — `cpe:2.3:<part>:<vendor>:<product>:<version>:<update>:<edition>:<language>:<sw_edition>:<target_sw>:<target_hw>:<other>`\n\n### Execution-context dimensions captured\n\n| CPE `part` Value | Meaning | Maps to Your Enum |\n|---|---|---|\n| `a` | Application (software app) | `server_side` if daemon/network; `client_side` if user-facing app |\n| `o` | Operating System | `local` for OS-level exploits; `server_side` if OS daemon |\n| `h` | Hardware (physical devices, chips) | `local` (AV:P); add `iot` / `ot` for firmware CVEs |\n| `c` | **Container** (grouping/legacy; not \"Docker container\") | Note: `c` in CPE 2.3 means \"Container\" as a deprecated group, NOT OCI containers |\n| `d` | Device (firmware) | `firmware` — not in your current enum |\n| `s` | Software (non-OS, non-app) | ambiguous |\n\n### What CPE does NOT provide\n- No delivery_vector\n- No exploit_complexity\n- `target_sw` and `target_hw` are optional extra qualifiers (e.g., targets a specific OS edition or hardware class)\n- CPE 2.3 has no \"cloud service\" part value — AWS/GCP/Azure services are `a` (application) even for IaaS primitives\n\n### How Phase 1 LLM could query it\n\nNVD CPE API supports filtering by `part` parameter. For a given CVE, list all CPE entries, extract the `part` values. Build a `part` → execution surface heuristic. Note: for firmware CVEs (`cpe:2.3:d:*`), mark `firmware` (add to enum).\n\n### Pros\n- Authoritative, covers every CVE with a CPE match\n- Structured API, machine-readable\n- `h` (hardware) explicitly differentiates physical/IoT/OT from software\n- `target_hw`/`target_sw` allow fine-grained targeting qualifiers\n\n### Cons\n- Multiple CPE matches per CVE (5-30 typical); disambiguation is noisy\n- CPE `part:c` is a deprecated grouping artifact, not Docker/OCI container classification — containerized workloads are usually `a` (application) in CPE 2.3\n- No delivery or exploit-complexity dimension\n- Requires API call per CVE or pre-cached dictionary\n\n**Recommendation for Phase 1:** Use CPE `part` as a secondary signal for `execution_surface`. When `part:h` appears, set `execution_surface = \"iot\"` or `\"ot\"` (add these values to enum). When all CPEs are `a` with server software names (e.g., `apache`, `nginx`), strengthen `server_side`.\n\n---\n\n## Source 4: MITRE CAPEC v3.9 STIX\n\n**Authoritative maintainer:** MITRE Corporation  \n**Schema:** STIX 2.1 (download at https://capec.mitre.org/data/downloads/capec_v3.9.zip or https://github.com/mitre/cti-capec)  \n**Object type:** `attack-pattern` (CAPEC entries)  \n**Bundle size:** ~1.2 MB JSON\n\n### Execution-context dimensions captured\n\nCAPEC STIX attack-pattern objects carry these MITRE custom fields (prefixed `x_capec_`):\n\n| Field | Content | Relevant to Your Enums |\n|---|---|---|\n| `x_capec_abstraction` | `Detailed`, `Pattern`, `Category` | Structural only |\n| `x_capec_likelihood_of_attack` | `High`, `Medium`, `Low` | Proximity to `exploit_complexity` |\n| `x_capec_typical_severity` | `Very High`, `High`, `Medium`, `Low` | Impact, not context |\n| `x_capec_consequences` | Structured list of `{consequence,scale,phase}` | Partial signal for outcome, not delivery |\n| `x_capec_skills_required` | List of `{skill_level,skills}` | Proximity to `exploit_complexity` |\n| `x_capec_related_weaknesses` | List of CWE IDs | CWE cross-reference |\n| `x_capec_resources_required` | Prose description of what attacker needs | Partial delivery context |\n| `x_capec_attack_prerequisites` | Prose list of conditions | Partial execution context |\n\n### Critical gap in CAPEC v3.9\n\nThere is **no** `attack_surface`, `execution_context`, `delivery_vector`, or `platform` field in CAPEC STIX. The `resources_required` and `attack_prerequisites` are free-text prose fields, not structured enums. The LLM cannot look up a structured value — it would have to parse natural language.\n\n### How Phase 1 LLM could query it\n\nMap CAPEC ID → CWE ID → execution context via your CWE_BEHAVIOR_MAP. CAPEC entries that reference CWE-829 (Supply Chain) correlate with `execution_surface=multi_hop`. CAPEC entries with `likelihood_of_attack=Low` and `skills_required` containing \"advanced\" correlate with `exploit_complexity=high`.\n\n### Pros\n- Strong CWE cross-references; CAPEC→CWE mapping provides execution-context signal through your existing CWE profiles\n- `x_capec_consequences` (structured) distinguishes confidentiality/integrity/availability impact\n\n### Cons\n- No structured execution_surface, delivery_vector, or exploit_complexity\n- `resources_required` and `attack_prerequisites` are prose — requires LLM parsing\n- ~600 entries, moderate coverage, but not all CVEs map cleanly to CAPEC\n- CAPEC union is too broad for technique-level mapping (confirmed by your `attack_mapper.py` comments)\n\n**Recommendation for Phase 1:** Use CAPEC as a CWE-level signal only — not as a direct lookup for your 4 enums. CAPEC→CWE→CWE_BEHAVIOR_MAP is your current path; CAPEC does not add new enum values.\n\n---\n\n## Source 5: MITRE ATT&CK Domain-Specific Matrices\n\n**Authoritative maintainer:** MITRE Corporation  \n**Matrices:** Enterprise ATT&CK, Mobile ATT&CK, ICS ATT&CK, ATT&CK for Containers  \n**URL:** https://attack.mitre.org/matrices/\n\n### How domains encode execution context\n\nEach matrix is a distinct ATT&CK bundle with its own `x_mitre_domain`. A technique's domain membership is a strong execution-context signal:\n\n| Domain | Matrix Focus | Execution Context Implied |\n|---|---|---|\n| `enterprise-attack` | Traditional IT (Windows, Linux, macOS, Cloud, Containers, Network) | `server_side`, `client_side`, `cloud`, `container` |\n| `ics-attack` | Industrial Control Systems (PLCs, RTUs, HMI, SCADA) | `ot` — add to enum |\n| `mobile-attack` | Android, iOS | `mobile` — add to enum |\n| *(Containers merged into Enterprise v18)* | Container orchestration (Docker, Kubernetes, OCI) | `container` / `api` |\n\n### Key technique-only-in-domain markers\n\n- **ICS-exclusive:** T0801–T0899 range. E.g., T0802 (Modify Tag Function), T0860 (Remote System Discovery). No equivalent in Enterprise.\n- **Mobile-exclusive:** T1400–T1499 range. E.g., T1447 (Delete Device Data).\n- **Container/Kubernetes (Enterprise):** T1609–T1613. E.g., T1611 (Escape to Host).\n- **Cloud-account specific:** T1078.004 (Valid Accounts: Cloud Accounts) — platform=`AWS,Azure,GCP`.\n\n### How Phase 1 LLM could query it\n\nFor a given CVE's ATT&CK technique set, check which bundle/domain each technique appears in. ICS-only technique → `execution_surface=ot`. Mobile-only technique → `execution_surface=mobile`. Container techniques → `execution_surface=container`. Cloud account techniques → `execution_surface=cloud`.\n\n### Pros\n- Domain membership is definitive — technique only exists in one matrix\n- ATT&CK v18 merged Cloud and Containers into Enterprise, so AWS/Azure/GCP/Containers are first-class Enterprise platforms\n\n### Cons\n- Requires having mapped to ATT&CK techniques first — Phase 1 does not yet do this\n- Domain resolution requires the full technique→domain mapping table (pre-computed, ~600 entries)\n- No delivery_vector or exploit_complexity\n\n**Recommendation for Phase 1:** If Phase 1 runs ATT&CK lookup (or uses CWE→ATT&CK from your `attack_mapper.py`), add domain resolution as a post-processing step. Map domain→enum value. Requires extending `ExecutionSurface` enum with `CLOUD`, `CONTAINER`, `MOBILE`, `OT` values.\n\n---\n\n## Source 6: CWE (Common Weakness Enumeration)\n\n**Authoritative maintainer:** MITRE Corporation  \n**Spec:** CWE List (https://cwe.mitre.org/)  \n**Schema:** CWE XML/JSON export (https://cwe.mitre.org/data/index.html)\n\n### Execution-context dimensions captured\n\nCWE does **not** have an exploitation-context taxonomy. The closest concepts are:\n\n| CWE | Name | Execution Context Signal |\n|---|---|---|\n| CWE-664 | Improper Control of Resource Lifecycle | Parent of many execution-context weaknesses; no structured field |\n| CWE-693 | Protection Mechanism Failure | Same — parent concept, not a classification |\n| CWE-829 | Inclusion of Functionality from Untrusted Control Sphere | **Direct signal for `execution_surface=multi_hop`** |\n| CWE-94 | Code Injection | Server-side interpreted language → `server_side` |\n| CWE-502 | Deserialization of Untrusted Data | Server-side → `server_side`; can be `client_side` for Java applet |\n| CWE-306 | Missing Authentication for Critical Function | `server_side`; pre-auth → `remote_network` |\n| CAPEC-549 | Local Execution of Code | Explicit `local_execution` → `execution_surface=local`, `delivery_vector=local_execution` |\n\n### Critical gap in CWE\n\nCWE has no `exploitation_context` field, no `attack_surface` field, no `delivery_vector`. The `Applicable_Platforms` element (in CWE XML) lists OS/language applicability (e.g., \"Linux\", \"Windows\", \"PHP\"), but this is deployment context, not exploitation context.\n\n### How Phase 1 LLM could use it\n\nYour `cwe_mapper.py` already has this mapping. CWE→`mandatory_behaviors` are prose strings, not structured enums. Add `CWE-829` detection (already partially done via `exploit_classifier.py` lines 79-80) as the authoritative signal for `multi_hop`.\n\n---\n\n## Source 7: OWASP Attack Surface Resources\n\n**Authoritative maintainer:** OWASP Foundation  \n**Resources:** OWASP ASVS 5.0, OWASP MAST (Mobile), OWASP Testing Guide, OWASP SAMM\n\n### Execution-context dimensions captured\n\nOWASP does **not** have a structured taxonomy mapping attack patterns to execution context. However, ASVS chapters provide implicit categorization:\n\n| ASVS Chapter | Execution Context |\n|---|---|\n| V4 (Architecture) | System-level (multi-tier) |\n| V5 (Authentication) | Server-side |\n| V9 (Communication) | Client↔Server |\n| V12 (File Handling) | Server-side (file upload) |\n| V7 (Access Control) | Server-side / API |\n| V14 (Configuration) | Server-side |\n| MAST (Mobile) | Mobile (`android`, `ios`) |\n\nOWASP defines attack surfaces as: **client, server, API, database, file system, hardware, wireless, physical** — but these are not machine-readable enumerations.\n\n### How Phase 1 LLM could use it\n\nUse ASVS chapter/control descriptions as a semantic knowledge base for `execution_surface` inference. For example: \"ASVS V12 file upload\" → `server_side`; \"ASVS MAST\" → `mobile`.\n\n### Pros\n- Covers API (`client_side` ↔ `server_side` bridge) and wireless contexts not found in other sources\n- OWASP MAST explicitly addresses mobile (Android/iOS) execution context\n\n### Cons\n- Not machine-readable; requires LLM to read and interpret prose\n- No structured delivery_vector or exploit_complexity\n- No cloud/container/firmware dimension\n- No authoritative API or STIX bundle\n\n**Recommendation for Phase 1:** Use OWASP as a secondary LLM prompt enrichment source, not a structured lookup. Include OWASP MAST mobile categories in the prompt when `execution_surface=mobile` is suspected.\n\n---\n\n## Source 8: STIX 2.1 Custom Object Extension (`x-` prefix)\n\n**Authoritative maintainer:** OASIS CTI TC (schema); MITRE (ATT&CK extensions)  \n**Spec:** STIX 2.1 Specification (OASIS Standard)\n\n### What custom objects allow\n\nSTIX 2.1 permits custom properties via the `x_` prefix (e.g., `x_mitre_platforms`, `x_capec_likelihood_of_attack`). Any organization can define `x_cve_execution_surface`, `x_cve_delivery_vector`, `x_cve_exploit_complexity` as custom properties on `vulnerability` objects.\n\n### How MITRE ATT&CK uses it\n\nMITRE's STIX bundle defines these custom fields on `attack-pattern`:\n- `x_mitre_attack_spec_version` — ATT&CK spec version\n- `x_mitre_domain` — matrix domain\n- `x_mitre_platforms` — platform list\n- `x_mitre_version` — technique version\n- `x_mitre_deprecated` — deprecation flag\n- `x_mitre_old_attack_id` — deprecated ID mapping\n\n### How Phase 1 LLM could use it\n\nYou could define a local STIX bundle (or JSON lookup table) with your 4 enum values as custom `x_cve_*` properties on `vulnerability` objects for known CVEs. This is a **curated local reference**, not an authoritative external source.\n\n### Pros\n- Full flexibility — define any enum values you need\n- Works offline after initial build\n- Can encode your existing `exploit_classifier.py` rules as machine-readable STIX properties\n\n### Cons\n- Requires building and maintaining the reference dataset yourself\n- Not authoritative — does not resolve `unknown` cases\n- Token cost for the initial build\n- Freshness depends on your update cycle\n\n**Recommendation for Phase 1:** Use as a **local curated reference** — pre-encode known CVE→enum mappings (e.g., all CVEs with CWE-829 → `multi_hop`) in a JSON lookup table, then fall back to rule-based classification for unknowns.\n\n---\n\n## Consolidated Findings: Gap Analysis\n\n| Your Enum | Authoritative Source | Available Values | Missing Values (Your Enum) |\n|---|---|---|---|\n| `exploit_vector` | CVSS 4.0 AV | `remote_network`, `adjacent_network`, `local`, `physical` | **None — your 3-value enum is the bottleneck** |\n| `exploit_complexity` | CVSS 4.0 AC | `low`, `high` | **`medium` is CVSS 3.x only — drop it or handle as-is** |\n| `execution_surface` | ATT&CK `x_mitre_platforms` + domain | `client_side`, `server_side`, `local` (from keywords) | **`cloud`, `container`, `api`, `wireless`, `firmware`, `iot`, `ot`** |\n| `delivery_vector` | None | — | **No authoritative source provides this** |\n\n### Priority Recommendations\n\n1. **Extend `ExecutionSurface`** enum to include `CLOUD`, `CONTAINER`, `API`, `MOBILE`, `OT`, `IOT`, `FIRMWARE`, `WIRELESS`. Source: ATT&CK `x_mitre_platforms` domain membership.\n\n2. **Drop `medium` from `exploit_complexity`**. CVSS 4.0 confirms `AC` only has `L` and `H`. Existing CVSS 3.x vectors with `AC:M` should be mapped to `high` (worst-case) or kept as-is for auditability.\n\n3. **`delivery_vector` has no authoritative source.** The best proxy is a keyword→vector heuristic (your current `exploit_classifier.py` approach). Consider building a local reference from the NVD advisory text annotated with delivery types (e.g., \"email attachment\" → `email_attachment`, \"web download\" → `web_download`).\n\n4. **`exploit_vector` your 3-value enum is too narrow.** Your code in `exploit_classifier.py` already produces `remote_network` / `adjacent_network` / `local` / `physical` — but `llm_contracts.py` only accepts `Literal[\"remote\", \"local\", \"unknown\"]`. **Fix the Pydantic constraint first** to allow `remote_network`, `adjacent_network`, `physical`.\n\n5. **ATT&CK domains** (enterprise/mobile/ics) are the best single signal for `execution_surface`. Add domain resolution as a Phase 1 post-processing step — not as an LLM lookup but as a rule: if Phase 1 output includes ATT&CK technique IDs, map those IDs to domain/platform via the ATT&CK STIX index.\n\n6. **CPE `part:h`** is the authoritative signal for IoT/OT hardware. When CPE entries include `h` for a hardware vendor (Cisco, Schneider, Rockwell), set `execution_surface=ot` or `iot`.
