Freshness Lag\n\n**Risk:** NVD CPE data is updated within hours of CVE publication, but the loader's baseline override file ships with the codebase. If a CVE is published with unusual CPE matches (e.g., a new cloud provider), the loader may not recognize it until the baseline file is updated.\n\n**Mitigation:** The primary inference path (CPE keyword matching against a dynamic keyword set) does not require shipping per-CVE entries. Only unusual edge cases need baseline overrides. Set a 7-day cache TTL (same as MITRE whitelist) for any future per-CVE JSON overlay file.\n\n### 2. Schema Drift (LLM vs. Rule-Based Inconsistency)\n\n**Risk:** Phase A (rule-based) and Phase B (LLM with augmented prompt) may produce different enum values for the same CVE. If the LLM sees the platform-inference table and produces `cloud` but the rule-based path produces `server_side`, downstream consumers see inconsistent data.\n\n**Mitigation:** The platform-inference table in the prompt explicitly maps `cloud` → `server_side`. Both paths converge on the same valid enum values. The mapping is documented in the table and in the loader's `infer_execution_surface()` source code. Phase C (schema expansion) is the only path that eliminates this risk.\n\n### 3. Multi-Source Conflicts\n\n**Risk:** A CVE has conflicting CPE signals (e.g., both `kubernetes` AND `physical` keywords present). The loader's priority order (CWE-829 → CPE vendor → CPE part → CVSS → description keywords) may not match the analyst's intent.\n\n**Mitigation:** The loader returns a confidence score (`PlatformInference.confidence`). When confidence < 0.6, fall through to the existing `classify_execution_surface()` keyword heuristics. The rule-based path is never short-circuited by the loader — it only enriches when the LLM output is absent or invalid. Document the priority order in the loader docstring.\n\n### 4. LLM Over-Reliance on Lookup Table\n\n**Risk:** The LLM memorizes the platform-inference table and stops reasoning from the CVE description, always picking the enum value associated with a keyword even when the description contradicts the keyword. For example: a CVE about a Kubernetes API server SSRF gets `multi_hop` from the table even though the description says \"remote unauthenticated HTTP request\" (which is `server_side`).\n\n**Mitigation:** The table's \"Notes\" column includes the reasoning. The prompt instruction says \"This table overrides generic heuristics for these platforms\" — which means the LLM should still derive from the description, using the table only to map the correct enum value when the platform signal is confirmed. Phase B A/B testing must measure false-positive rate (LLM outputting `multi_hop` for non-supply-chain CVEs).\n\n### 5. File Size (Baseline Override JSON)\n\n**Risk:** If Phase A ships a per-CVE override JSON with thousands of entries (one per CVE), the file becomes large and slow to load. The MITRE STIX loader already loads a ~30-50MB file — adding another large JSON file increases cold-start time.\n\n**Mitigation:** Phase A ships zero per-CVE entries. The baseline override file contains only manually verified entries for the 5+ missing enum value categories (cloud, container, api, iot, adjacent_network) — estimated < 50 entries. If the override file grows beyond 1,000 entries, switch to a CPE-prefix-keyed dictionary (load only entries matching the current CVE's vendor prefix) rather than a full CVE-ID-keyed dictionary.\n\n---\n\n## Summary: Changes Required for Phase A (Rule-Based Path Only)\n\n| File | Change | Impact |\n|---|---|---|\n| `src/shared/platform/loader.py` | New file — `CvePlatformWhitelist` singleton | Zero runtime impact until called |\n| `src/shared/platform/baseline_overrides.json` | New file — <50 manually verified entries | Zero runtime impact until called |\n| `src/usecases/step_2_analysis/orchestrator.py` | Call `CvePlatformWhitelist.get().infer_execution_surface()` in `_normalize_phase1_dict()` | Additive enrichment; existing fallback path preserved |\n| No changes | `analyze_behavior_phase1.system.txt` | Phase B |\n| No changes | `llm_contracts.py`, `schemas.py`, Pydantic models | Phase C |\n| No changes | `phase1_service.py`, `attack_mapper.py`, `attack_validator.py` | Existing paths untouched |
